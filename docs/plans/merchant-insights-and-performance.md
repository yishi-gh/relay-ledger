# 商家分析与性能实验计划

本计划对应 2026-11-11 的第 8、9 项需求。两个实验各自提交，保留待审批，不合并、不部署到生产。自动归属与第 1—7 项基础界面调整另行交付。

## 执行顺序

1. 核对官方文档、源码和现有数据字段，记录可复核来源。
2. 做商家分析预览，模块可以单独显示或移除，沿用已有真实接口。
3. 先测量页面切换、首屏和 SQL，再实施有证据的性能优化。
4. 验证数据、异常、响应式和性能差异，分别提交实验分支。
5. 提供本地可打开的预览、对照结果和取舍说明，由用户选择合入内容。

## 商家分析

分支：`experiment/merchant-insights`；目录：`.slim/worktrees/merchant-insights`。

调研以 NewAPI、Sub2API、CC Switch、LiteLLM、厂商用量页面和 Magpie 为主要来源。Codex++ 同名项目的实际用途需核实，不能只凭项目名称推断功能。

候选模块：

- 账户经营：收入、余额核算成本、利润、毛利率与覆盖情况。
- 毛利构成和成本波动：完整账期的经营瀑布、账户日成本变化。
- 上游质量：成功率与延迟散点、错误构成、首 Token 延迟。
- 单位 Token 收入：比较模型与渠道的收入结构，不冒充毛利。
- 收入集中度：头部账户、渠道和模型的依赖程度。
- 余额与对账：最早耗尽账户，以及上游自报消费与余额推导成本的差异。

现有接口能计算的模块先做；缺少真实字段的指标只补必要的只读聚合，不制造数据。预览应同时能展示真实缺失状态和标明来源的隔离样本，以便评估视觉设计。

## 性能实验

分支：`experiment/panel-performance`；目录：`.slim/worktrees/panel-performance`。

优先测量：

- 余额页是否重复请求主加载已有的数据。
- 模型、健康、路由、系统页面反复进入的网络请求与就绪时间。
- 首屏是否被当前页面不需要的请求阻塞。
- 大量日志下分组、用户查询的执行计划与耗时。
- 路由页独立代码块对初始资源和首次进入速度的影响。

每项优化保留相同输入、返回值校验和及冷/热对照。先分开验证，再决定是否组合，不能只报告包体缩小而忽略首次进入变慢。

## 验收与边界

- 使用临时数据库和本地预览；不改 NewAPI 代码，不在生产执行压力查询。
- 不按渠道收入比例分摊账户成本，不把参考价或估算花费当成真实扣费。
- 缺快照、无错误覆盖和旧窗口数据保持可辨认，不能用缓存制造成功状态。
- 同一查询窗口下财务总额、归属和关键错误行为保持一致。
- 每个预览模块有独立入口或开关，不强制捆绑采用。
- 桌面、手机、明暗主题均检查，保留用户当前个人偏好和表格能力。
- 实验分支分别提交，交付提交号、预览地址、验证证据及未采用部分；审批前不合并。
